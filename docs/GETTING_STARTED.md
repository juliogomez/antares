# Getting started

Three ways to engage with Antares, from lightest to heaviest. 

| Step | You get… | Needs install? | ~Time |
|---|---|---|---|
| **0** | A worked example of what the agent does | No | 15 min |
| **1** | Live run on **your** repo; model output in the terminal | Mac, HF, Docker | 2–5 min |
| **2** | Official benchmark score; output in **JSON files** | Step 1 + harness + zips | 1 min – 9 h |

**Headline numbers (499 repos)** are already in the repo. You do not need step 2 `full` to see them; jump to [Pre-run full sweep results](#pre-run-full-sweep-results) below.

Requirements for steps 1 and 2: Apple Silicon Mac, Python 3.13+, Docker, Hugging Face access to [fdtn-ai/antares-1b](https://huggingface.co/fdtn-ai/antares-1b).

## Step 0: Read a saved run (no install)

Antares gets a CWE description and a repo, then **searches iteratively**: up to 15 read-only shell commands, reading each result and adjusting strategy before submitting a ranked file list. This step walks through that loop on a real benchmark repo without running anything.

**Repo:** [tokio-rs/slab](https://github.com/tokio-rs/slab), manifest entry [`Kv0mIk0C`](https://github.com/cisco-foundation-ai/vulnerability-localization-benchmark/blob/000c19cda9ba027e1d241216768b2b6358685000/data/manifest.csv#L2725), **CWE-119**.

Open [traces/antares-slab-phase-a.json](traces/antares-slab-phase-a.json) in an editor while you read below. Top-level keys: `result` = scores, `trace` = conversation.

### Where reasoning and tool calls come from

Each assistant message in the trace is **two layers**: fixed runner plumbing, then **model-generated** content. That split is the core of the product—the harness is a thin loop; Antares supplies the investigation policy.

| Layer | Who provides it | What it is |
|---|---|---|
| **Task framing** | Runner (static) | System prompt: “localize this CWE,” tool names, sandbox rules. User message: your CWE description. Same template every run ([`minimal_agent.py`](../minimal_agent.py), official harness). |
| **Thinking opener** | Runner (static) | Before each completion, the runner prompt ends with the `<think>\n` opener, so the model continues it in “reason first, then act” format. |
| **Reasoning text** | **Antares (dynamic)** | Everything until the closing `</think>` (e.g. “Locate memory-unsafe code or buffer operations.”) is **new text every turn**, from the weights, based on CWE + conversation so far. Not scripted by the loop. |
| **Tool call** | **Antares (dynamic)** | The `<tool_call>{"name": …, "arguments": …}</tool_call>` block: which tool (`terminal`, `submit_vulnerable_files`, …) and the exact command or file list. Also **generated each turn**—not picked from a menu by the runner. |
| **Execution** | Runner (static) | Regex-parse the first tool call, validate command, run in Docker, append `<tool_response>` to the conversation. Feed the updated transcript back to the model for the next turn. |

There is **no separate “tool API”** or constrained decoder. Antares was trained (SFT + GRPO on VLoc trajectories) to emit tool calls as **plain completion text** inside those XML tags; the runner parses them like any other string ([INTERNALS.md](INTERNALS.md)). Cisco disabled mlx-lm’s tool parser so those tags are not stripped at serve time.

So **both the reasoning and the tool call are dynamically generated by Antares.** The runner’s job is to (1) set up the prompt, (2) prefill the thinking opener, (3) execute whatever the model asks, (4) stop when budgets run out or the model submits. The value is the trained multi-turn policy—choosing the next sub-question, mapping CWE language to repo-specific searches, and adapting when a command is rejected or returns nothing.

In step 1, `--show-thinking` prints the model-generated reasoning; without it you still see a truncated preview each turn.

### What happens

Each assistant turn has two parts: a **reasoning block** (`<think>`) stating the current investigation goal, then a **tool call**. The model reads the tool output and decides the next goal. On this episode (13 terminal calls, F1 1.0) the arc looks like this:

#### 1. Orient in the repo

**Reasoning:** “Start by identifying the project structure and key source files.”

The model assumes a normal shell workflow (`cd … && ls`), but the harness rejects `&&`, then rejects bare `cd`. It does not repeat the same mistake—it **re-plans** and runs `find . -maxdepth 2`, which reveals `src/lib.rs`, `src/builder.rs`, `src/serde.rs`, and tests. It spends exploration budget learning the project structure before hunting for the vulnerability.

#### 2. Translate CWE-119 into Rust-specific signals

**Reasoning:** “Locate memory-unsafe code or buffer operations.”

CWE-119 is generic buffer-boundary language. Antares maps it to Rust idioms: `unsafe`, raw pointers (`ptr::`, `from_raw`), `copy_nonoverlapping`, unchecked indexing. It first tries one broad `rg` with alternation (`unsafe|from_raw|ptr::|…`).

That command is rejected—the harness treats tokens inside the pattern as forbidden subcommands ([upstream/ISSUE.md](../upstream/ISSUE.md)), not because the search idea was wrong. **Adaptation:** drop the compound regex; run a minimal `rg -n "unsafe" src tests`. That succeeds and surfaces line hits only in `src/lib.rs` (e.g. `entries_ptr.add(key)`, `get_unchecked`, `get2_unchecked_mut`).

#### 3. Confirm and narrow (including dead ends)

**Reasoning shifts turn by turn:** “Locate raw pointer usage” → “Locate memory buffer operations” → “Locate buffer allocation and pointer arithmetic code.”

Follow-up greps for `ptr::` and `copy_nonoverlapping` return **no output**. A weaker model might keep widening; here the prior hit already concentrated risk in `src/lib.rs`, so the next moves **double down** on that file (`grep … src/lib.rs`, then `rg … src/lib.rs`). Same lines, stronger confidence.

With a few calls left, it **reads context**, not just match lines: `nl -ba src/lib.rs | sed -n '700,900p'` pulls the surrounding implementation around the unsafe blocks before committing.

#### 4. Submit with an explicit hypothesis

**Reasoning:** “Locate the unsafe pointer manipulation code that may perform out-of-bounds buffer access.”

It calls `submit_vulnerable_files` with `["src/lib.rs"]`—one file, ranked first—matching the patch ground truth.

---

**Takeaways from this trace**

| Pattern | What you see here |
|---|---|
| **Goal-directed turns** | Each thinking block names the next sub-question, not “run another grep.” |
| **CWE → language mapping** | Generic CWE text becomes ecosystem-specific search terms. |
| **Recover from sandbox errors** | Rejected commands → simpler syntax or different tool, same intent. |
| **Use negative evidence** | Empty `grep` results shrink the hypothesis space instead of random new paths. |
| **Read before submit** | `sed` slice of source precedes the final answer. |

Expand every `<think>` block in the JSON while you read—the prose inside is **model output**, not a template (see [Where reasoning and tool calls come from](#where-reasoning-and-tool-calls-come-from)). The commands alone look like regex; the reasoning chain is the search policy Antares was trained for ([VALUE.md](VALUE.md)). The benchmark grades **paths only**, not that narrative.

Score still depends on harness rules as much as the model. In production you would verify the file; the list is a triage hint.

## Step 1: Run on a repo you choose

[`minimal_agent.py`](../minimal_agent.py) is a readable copy of the agent loop. It prints thinking and commands **in your terminal**. Use any local directory and any CWE string. There is no ground-truth scoring and no result JSON. For what the runner supplies vs what the model generates each turn, see step 0 ([Where reasoning and tool calls come from](#where-reasoning-and-tool-calls-come-from)).

The agent still runs **shell commands the model wrote**. Those execute inside the same Docker sandbox the benchmark uses: repo mounted read-only, no network, non-root user, allowlisted tools. The `docker build` line builds that sandbox image; it is for **safety**, not for benchmark scoring. Step 2 adds harness + zips on top of this.

### One-time setup

```bash
python3 -m venv .venv && source .venv/bin/activate
pip install mlx-lm huggingface_hub requests pyyaml tqdm
hf auth login                              # accept gate on fdtn-ai/antares-1b
python scripts/build_mlx_shim.py
./scripts/fetch_benchmark.sh               # clones vendor/vloc-bench (Dockerfile only for step 1)
docker build -t vulnerability-localization-benchmark-sandbox vendor/vloc-bench
```

Re-run `source .venv/bin/activate` in every new terminal. Step 1 does **not** need benchmark zip downloads or `run_eval.py`.

### Run (two terminals)

**Terminal A** — start the model server (leave it running):

```bash
./scripts/serve.sh antares
```

**Terminal B** — run the agent:

```bash
git clone --depth 1 https://github.com/tokio-rs/slab /tmp/slab
python minimal_agent.py --repo /tmp/slab \
  --cwe "CWE-119: Improper Restriction of Operations within the Bounds of a Memory Buffer"
```

Add `--show-thinking` to print the full reasoning block each turn (the narrative Cisco demos often highlight alongside file paths).

Same repo as step 0; compare terminal output to the saved trace. Quick check on this repo: `python minimal_agent.py --repo . --cwe "CWE-22: Path Traversal"`.

From an advisory: look up the CWE, paste the class description into `--cwe`—the model does not ingest GHSA/NVD IDs directly ([VALUE.md](VALUE.md)).

## Step 2: Official benchmark score

[`run_eval.py`](../scripts/run_eval.py) drives Cisco’s harness on **benchmark repos only**. It uses the same model and sandbox rules as step 1, but:

- Output goes to JSON under [`runs/antares-<subset>/`](../runs/), not your terminal.
- Scores are compared to patch ground truth (see [PROTOCOL.md](PROTOCOL.md)).

Read step 0 first so the trace JSON makes sense. Optional after a run: [RESULTS.md](RESULTS.md).

### One-time setup (in addition to step 1)

Step 1 already ran `fetch_benchmark.sh` and built the sandbox image. If you skipped step 1, run `./scripts/fetch_benchmark.sh` and the `docker build` line from step 1 first.

Step 2 adds **benchmark repo zips** on disk (below). That is what step 1 does not need.

### Pick a subset

| `--subset` | Repos | Output dir | ~Run time | Purpose |
|---|---|---|---|---|
| `demo` | 1 (slab) | [`runs/antares-demo/`](../runs/antares-demo/) | ~1 min | Same repo as [step 0](#step-0-read-a-saved-run-no-install) |
| `lab` | 3 | [`runs/antares-lab/`](../runs/antares-lab/) | ~2 min | Small mix (npm, pip, rust) |
| `smoke` | 5 | [`runs/antares-smoke/`](../runs/antares-smoke/) | ~2 min | Quick stack check |
| `full` | 499 | [`runs/antares-full/`](../runs/antares-full/) | ~9 h | Reproduce the study from scratch |

Each subset has a matching id list (`configs/<subset>_ids.txt` → `data/<subset>_manifest.csv`) so you download and run only those benchmark entries instead of all 499. `run_eval.py --subset demo` picks this manifest automatically; the downloader needs the same CSV to fetch the matching repo zips.

### Download repo zips (once per subset)

Replace `demo` with your subset name (`lab`, `smoke`). For `full`, skip `make_subset` and use `vendor/vloc-bench/data/manifest.csv` as the manifest path.

```bash
python scripts/make_subset.py --ids configs/demo_ids.txt --out data/demo_manifest.csv
python vendor/vloc-bench/data/downloader_and_verifier.py \
  --manifest data/demo_manifest.csv --output-dir data/ghsa-vulns
```

### Run (two terminals)

**Terminal A:** `./scripts/serve.sh antares` (if not already running from step 1).

**Terminal B:**

```bash
python scripts/run_eval.py --model antares --subset demo --phases a
# lab:  --subset lab
# smoke: --subset smoke
```

`run_eval.py` prints config lines, then the harness runs. It does **not** show model reasoning on stdout.

### Read the results

Look in the output dir for your subset (example: `demo` → [`runs/antares-demo/`](../runs/antares-demo/)):

| File | Contents |
|---|---|
| [`aggregate.json`](../runs/antares-demo/aggregate.json) | Summary: mean file F1, abstain rate, entry count |
| [`Kv0mIk0C_phase_a.json`](../runs/antares-demo/Kv0mIk0C_phase_a.json) | Scores for one repo: `file_f1`, `submitted_files`, `ground_truth_files` |
| [`Kv0mIk0C_phase_a_trace.json`](../runs/antares-demo/Kv0mIk0C_phase_a_trace.json) | Full transcript (same layout as step 0) |

```bash
cat runs/antares-demo/aggregate.json
cat runs/antares-demo/Kv0mIk0C_phase_a.json
```

**`Nothing to do!`** — the harness skips repos that already have result JSON (`--resume` is always on). Your scores are already in the files above; you did not just get an empty run.

**Re-run from scratch:** delete `*_phase_*.json` in that output dir, or pass `--out runs/antares-demo-rerun`.

## Full sweep (optional)

Only if you want to **reproduce** the 499-repo run yourself (~**9 hours** on a 24 GB Apple Silicon Mac with one model server, `--phases a`). Keep the Mac awake; use `daemon.py` so a dropped SSH session does not kill the job:

```bash
python scripts/daemon.py --name sweep -- \
  python scripts/run_eval.py --model antares --subset full --phases a
```

After it finishes, aggregate with [`analyze.py`](../scripts/analyze.py):

```bash
python scripts/analyze.py runs/antares-full --markdown
```
